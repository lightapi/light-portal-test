# Workflow admin runtime fixtures

These files are declarative fixture specifications. They are not executable tests by themselves. They describe state that a deployment driver must establish through supported Workflow/Gateway starts and prohibit direct SQL setup and unbounded waits. The assigned-ask fixture has no agent or repository effects. The between-stage VM fixture uses the existing Phase 1 intake/design workflow, which may call agents/models and write to its configured repository workspace. The driver must record the target and observed effects and clean up fixture-owned resources. `contract` mode validates the specification and does not qualify current-state runtime behavior.

No deployment driver is included in Phase 0 yet. Runtime qualification therefore remains open. Live execution requires an executable driver named by `WORKFLOW_ADMIN_FIXTURE_DRIVER`. The driver receives `--fixture <absolute fixture.json> --mode runtime --evidence <output.json>` and must call light-gateway directly. In `portal-config-loc/all-in-lt`, the external Gateway MCP endpoint is `https://localhost/mcp`; `https://localhost:3000` is the Portal UI origin and does not qualify the Gateway boundary. The driver must return nonzero for missing/skipped assertions or timeouts and write sanitized machine-readable evidence. Database queries may verify state after supported starts; they may not create or repair it.

The normative CLI, exit-code, atomic-output, evidence-schema, and required-assertion contract is documented in `implementation/light-portal/workflow-admin-runtime/phase0/README.md`. When the driver lands, current-state runtime mode must become a PostgreSQL-backed CI job; contract-only `make validate` intentionally does not claim runtime qualification.

`assigned-ask` must prove USER assignment creation, authorized Portal visibility, claim/release/complete behavior, and exactly one continuation. ROLE membership freshness is a separate Phase 0 acceptance gate; this fixture does not claim to qualify ROLE assignments.

`between-stage-vm` must prove completed Phase 1 intake/design stage invocations, no running invocation, retained VM reservation, feature discovery, version-fenced feature cancellation, and positive release evidence. Cancellation acceptance alone is insufficient. Model and repository effects are permitted for this fixture; record their targets and cleanup outcome in sanitized evidence.
